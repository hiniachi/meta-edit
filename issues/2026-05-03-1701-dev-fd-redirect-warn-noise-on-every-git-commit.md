# [UX] every `git commit` / `gh pr create` heredoc emits a structural redirect-warn

## Status

🟡 **PARTIAL** via PR #61 (merged 2026-05-02, commit `67d955c`).
Outer-segment `iterRedirectTargets` now tracks substitution depth
via opt-in `skipSubstitutionInternal`, plumbed through
`redirectsOutsideSafeSinkAllowlist`. Outer-segment case is silenced;
recursive-inner pseudo-segments from heredoc bodies still surface
the warn. Heredoc-aware segmentation is the clean fix; deferred to
a follow-up. Option 2 of this filing landed in part.

## TL;DR

Every `git commit -m "$(cat <<'EOF' ... EOF)"` and `gh pr create --body
"$(cat <<'EOF' ... EOF)"` invocation triggers the v0.1.5 structural
redirect-warn:

> command redirects (`>` / `>>` / `>|`) to a path outside the safe-sink
> allowlist (/dev/null, /tmp/, /var/tmp/, /run/, /sys/). For in-repo
> writes prefer an edit_* tool …

The redirect in question is **shell-internal heredoc plumbing**
(`/dev/fd/63` or similar), not a user-typed write. The user typed
zero `>` characters; the substitution `$(cat <<'EOF' ... EOF)` is
how bash plumbs the heredoc into command-substitution stdout, and
that internally creates a `>` redirect to a process-FD alias.

In PR #60's authoring session this warn fired on every single git
commit (5+ times). Each time it surfaces as a `system-reminder` in
the agent's context window, consuming attention that's not load-
bearing.

## Why this is LOW

- It's `warn`, not `deny`. Commits go through.
- It's an attention tax, not a behavior bug. The warn message itself
  is correct in principle (the redirect is structurally outside the
  allowlist); the issue is just that **the redirect was generated by
  the shell, not the user**, and there's no honest action the user
  can take to silence it short of avoiding command-substitution.

## Reproduction

```bash
# Anywhere the hook is installed:
git commit -m "$(cat <<'EOF'
hello
EOF
)"
# → warn fires; commit succeeds.
```

Or:

```bash
gh pr create --title "..." --body "$(cat <<'EOF'
body
EOF
)"
# → warn fires; PR is created.
```

Both forms are recommended in the project's own `Bash` tool guidance
(HEREDOC for multi-line commit messages and PR bodies — see the system
prompt's commit-formatting block), so the warn fires on the project's
own canonical commit invocation.

## Fix directions

The challenge is that we **cannot** broadly add `/dev/fd/`,
`/proc/self/fd/`, etc. back to the safe-sink allowlist — codex review
#31 narrowed those out specifically because they ARE viable write
targets when an attacker controls the FD (e.g. `exec 3>src/foo.ts;
echo hi | tee /dev/fd/3` writes to a repo file via FD aliasing).

Three narrower paths, none ideal:

1. **Suppress the warn when the redirect target is a process-FD alias
   AND no preceding `exec N>...` opens that FD.** This requires
   tracking FD opens across the segment, which is heavier than the
   structural check is meant to be. Probably overshoots the bar.
2. **Suppress the warn when the redirect lives inside a
   command-substitution (`$(...)` or backticks) rather than at the
   outer command level.** The user-typed `>` in `cat src > foo.ts`
   IS at the outer level; the heredoc-plumbing `>` lives inside the
   `$(...)` body. Distinguishable lexically. Doesn't help when the
   user types a `$(...)` containing a real bypass, but those are
   already covered by the recursive shell-hosted-payload scan.
3. **Demote heredoc-plumbing redirects from `warn` to silent allow.**
   Acceptable because the warn for that specific shape is never
   actionable — there's no AI-editable fix for "stop using
   command-substitution to assemble multi-line commit messages."
   The signal-to-noise of the warn is ~0 for this shape.

(2) feels like the right surface: track quote/substitution depth
when iterating redirect targets, and only warn for redirects at
substitution-depth 0. (3) is more aggressive and forfeits a real
(though narrow) bypass-detection surface — only worth doing if (2)
turns out to be too complex.

## Out of scope

- Bigger structural rework of how the hook handles
  command-substitution. The recursive shell-hosted-payload scan
  already catches `bash -c "..."` and `eval "..."`; extending that
  to `$(...)` would be a separate effort.

## Related

- Codex review #31 (PR before this one) — narrowed `/dev/fd/` /
  `/proc/.../fd/` out of the safe-sink allowlist. The fix here must
  not unwind that.
- The warn message contributes to the v0.1.5 → v0.2 "deny-restore

  plumbing to silent might make that signal slightly cleaner, since
  it's currently 100% noise.
